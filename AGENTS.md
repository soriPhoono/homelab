# AGENTS.md

Operational manual for agents working in this repository. The rules here
are mandatory, not advisory. Read it before changing anything.

## Orientation

This is a Nix flake configuring NixOS hosts, users and home-manager
homes. It is built on [den], [flake-parts] and [import-tree], and follows
the dendritic pattern: every `.nix` file under `modules/` is a
flake-parts module, auto-imported by `import-tree ./modules`. There is no
central import list — a file in `modules/` is part of the flake.

Configuration is expressed as _aspects_: composable units declared under
`den.aspects.*` and pulled into entities (hosts, users, homes) through
`includes`.

## Repo map

- `modules/aspects/` — reusable aspects, the bulk of the configuration.
- `modules/systems/nixos/<host>/` — per-host configuration, disko layout
  and the `facter.json` hardware report.
- `modules/systems/darwin/`, `modules/systems/wsl/` — future planning,
  currently empty scaffolding.
- `modules/users/<name>.nix` — `den.aspects.<name>` for a user.
- `modules/homes/<name>.nix` — `den.homes.<system>.<name>`.
- `modules/inputs.nix` — flake inputs.
- `flake-system/` — flake-parts plumbing: dev shell, pre-commit hooks,
  treefmt, systems, GitHub workflow generators.
- `secrets/` — sops-encrypted secrets. See [Secrets](#secrets).
- `.agents/wikis/` — research wikis. See [Research](#research-and-the-wiki).

## Never hand-edit generated files

- `flake.nix` is generated by flake-file. Declare inputs in
  `modules/inputs.nix`, or across the project using flake-file,
  then run `nix run .#write-flake`. Editing `flake.nix` directly
  is silently discarded on the next regeneration.
- `.pre-commit-config.yaml` is generated by git-hooks.nix and is
  gitignored. Change hooks in `flake-system/pre-commit-hooks.nix`.

## Aspect conventions

- One aspect per file, named after the aspect.
- `_private/` directories hold shared internals, imported explicitly with
  `imports = [ ./_private ];`. import-tree skips underscore paths.
- Optional layers become sub-aspects of the base aspect, for example
  `den.aspects.core.hardware.gpu.amd.gpgpu`, so hosts opt in per feature.
- An aspect's `nixos` attribute is a module: `nixos = { pkgs, ... }: { }`.
  A bare attrset also works. Use `_:` when no arguments are needed; the
  formatter rewrites `{ ... }:` to that.
- An aspect's `homeManager` attribute is also a module for Home Manager,
  it follows the same rules as the nixos module however contains Home Manager
  options for configuring a user environment when the aspect is applied to a
  home or host

## Gotchas

Each of these fails with a message that points somewhere unhelpful.

- **A functor aspect cannot carry sub-aspects.** Writing
  `den.aspects.x = { host, user, ... }: { ... }` is supported, and is how
  an aspect takes `host` or `user` parametrically. Sub-aspects declared
  inside a functor body are unreachable, though: including
  `den.aspects.x.sub` fails with `expected a set but found a function`
  at a nested path, or `attribute 'sub' missing` at the top level. Use a
  plain set when an aspect needs sub-aspects, taking `host` from the
  `nixos` module arguments there instead.
- **An aspect with only `includes` is not registered.** Referencing it
  then fails with `attribute '<name>' missing`, indistinguishable from a
  typo. Give it `nixos = _: { };` if it configures nothing.
- **`hasAspect` takes an aspect reference, not a string.** Passing
  `"core.hardware.gpu.amd"` throws
  `ref must have name+meta or __aspectChain (got string)`. Pass the
  aspect value itself: `den.aspects.core.hardware.gpu.amd`.
- **Untracked files are invisible to the flake.** A new file that has not
  been `git add`ed produces `attribute '<name>' missing` for everything
  it defines. Check `git status` before debugging the code.
- **Unfree packages are declared per aspect**, with
  `(den.batteries.unfree [ "pname" ])` in that aspect's `includes`.
  `unfree.packages` is a merging list, so several aspects can each
  declare their own without conflicting. Names are exact `lib.getName`
  matches, with no prefix matching.

## Verification gates

Run these in order before reporting that a change works. Stopping early
is not evidence. `<host>` is a directory under `modules/systems/nixos/`.

```sh
git add <new files>        # untracked files do not exist to the flake

nix-instantiate --parse <file>   # syntax only — NEVER sufficient alone

nix eval .#nixosConfigurations.<host>.config.system.build.toplevel.drvPath

nix eval .#nixosConfigurations.<host>.config.assertions \
  --apply 'a: map (x: x.message) (builtins.filter (x: !x.assertion) a)'
  # must print [ ]

nix fmt                    # the treefmt hook fails the commit otherwise
```

`nix flake check` is **not** a gate. It runs only `check-flake-file`,
`pre-commit` and `treefmt`; it never evaluates or builds the systems, and
passes happily on a completely broken host.

For changes that need to actually boot, use the VM:

```sh
nix run .#vm-laptop-ares
```

## Development patterns

- **Tooling goes in the dev shell**, never into host configuration. Add
  packages to the `EXTRA PKGS` list in `flake-system/shells/dev.nix` and
  enter with `nix develop`; direnv does this automatically.
- Pre-commit hooks run over every file in the repository with no path
  exclusions: treefmt, nil, markdownlint, editorconfig-checker,
  gitleaks, commitizen, actionlint and the whitespace fixers.
- Markdown is linted with markdownlint defaults, so **wrap prose at 80
  columns**, give every fenced block a language, and start each file with
  a single top-level heading.
- CI (`.github/workflows/flake-check.yml`) runs nix-fast-build over
  `checks`, `packages` and `devShells` on pull requests and pushes to
  `main`. Host breakage surfaces in the `packages` build, never in
  `checks`.
- `.github/workflows/update-flake-lock.yml` opens an input-bump pull
  request weekly, Sundays at 00:00.

## Secrets

Do not touch them. `secrets/` holds sops-encrypted files and `.sops.yaml`
holds the public age recipients.

- Never decrypt, re-encrypt, or run `sops updatekeys`.
- Never create or edit a secret file, and never commit plaintext.
- If a change needs a secret, describe what is needed and hand back.

A wrong recipient set locks a host out of its own secrets, and that fails
at boot rather than at evaluation.

## Git

- `git add` every new file before evaluating. See [Gotchas](#gotchas).
- Commits follow Conventional Commits; the commitizen hook rejects
  anything else.
- Never pass `--no-verify`. If a hook rewrites files, stage the result
  and commit again rather than bypassing it.

## Research and the wiki

Before researching anything externally, consult, in this order:

1. This file, and the wikis under `.agents/wikis/`.
2. Documentation shipped by the flake inputs and readable in the nix
   store: den's module doc comments, nixpkgs option `description`
   fields, upstream READMEs. These are authoritative and match the
   pinned revision.
3. The web.

Cite an existing article rather than re-deriving it. Re-derivation
produces a second, possibly contradictory article.

When external information is used, record it. A wiki lives at
`.agents/wikis/<subject>/`, kebab-case and named after the subject, never
after the task that prompted it. Each holds three directories:

- `raw/` — one file per source page.
- `entities/` — one file per named thing (`den.md`, `flake-parts.md`),
  opening with a one-line definition.
- `concepts/` — one file per idea or relationship, such as
  `aspect-resolution.md`, in the same shape.

Citations are web URLs or nix store code locations. Convert a source page
with:

```sh
pandoc -f html -t gfm-raw_html --wrap=auto --columns=80 page.html \
  -o .agents/wikis/<wiki>/raw/<slug>.md
markdownlint --fix .agents/wikis/<wiki>/raw/<slug>.md
```

Then prepend the article title as a top-level heading, the source URL and
the retrieval date. `-t gfm-raw_html` strips inline HTML, `--columns=80`
satisfies the line-length rule, and the heading satisfies the
first-line-heading rule.

## Recipes

Every recipe ends with the [verification gates](#verification-gates).

### Add an aspect

1. Create `modules/aspects/<path>/<name>.nix`.
2. Define `den.aspects.<path>.<name>` as a plain set with a `nixos`
   attribute.
3. `git add` the file.
4. Include it from a host, user or home, then run the gates.

### Add a host

1. Create `modules/systems/nixos/<host>/default.nix` declaring
   `den.hosts.<system>.<host>.users.<user> = { };` and
   `den.aspects.<host>.includes = [ ... ];`.
2. Add `disko.nix` for the disk layout, and `facter.json` from
   nixos-facter wired up with
   `hardware.facter.reportPath = ./facter.json;`.
3. `git add` the directory, then run the gates against `<host>`.

### Add a user

1. Create `modules/users/<name>.nix` defining `den.aspects.<name>`.
2. Reference the user from a host's `den.hosts.<system>.<host>.users`.
3. Per-host user aspects are named `"<user>@<host>"`.

### Add a home

1. Create `modules/homes/<name>.nix` defining
   `den.homes.<system>.<name>`.
2. `git add` the file, then run the gates.

## Anti-patterns

- **Do not hardcode what nixos-facter detects.** Facter already sets
  `boot.initrd.kernelModules` from the detected graphics cards, and
  `hardware.enableRedistributableFirmware` on bare metal. Hardcoding
  those duplicates per-host detection and picks the wrong driver on
  hardware you did not anticipate.
- **No global `environment.variables` for driver selection.** Variables
  such as `LIBVA_DRIVER_NAME` apply to every session and break
  hybrid-GPU hosts. libva maps the DRM kernel driver to the correct VA
  driver by itself.
- **No VDPAU.** Mesa ships no VDPAU driver at all, and `libvdpau-va-gl`
  is a dead shim onto VA-API.
- **No tooling in host configuration** when the dev shell will do.
